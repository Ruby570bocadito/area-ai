## Resumen
Mitigado el vector SSRF de `POST /api/models` con un guard de destinos (`src/lib/net/target-guard.ts`) que bloquea siempre los endpoints de metadata de nube, impide alcanzar redes internas desde conexiones remotas y exige https a proveedores cuando la petición no es local. La mitigación se verificó con 20 tests unitarios de las funciones puras y 5 smoke tests en caliente contra el servidor de producción real, incluyendo un caso legítimo (DeepSeek público) que atraviesa el guard correctamente.

## Análisis del vector
`POST /api/models` hace que **el servidor** realice un `GET {baseUrl}/models` con una `baseUrl` arbitraria del cuerpo. Solo validaba protocolo http(s) y timeout de 15 s. Un cliente remoto podía: sondear puertos internos (p. ej. el laboratorio en `127.0.0.1:4403`), alcanzar servicios de la LAN del servidor o leer endpoints de metadata de nube (169.254.169.254) si la app se desplegaba en una VM cloud. Con la respuesta JSON del endpoint se distinguían puertos abiertos/cerrados (escáner indirecto).

## Mitigación implementada

### Nuevo: `src/lib/net/target-guard.ts`
- `classifyTarget(hostname)`: clasifica el destino en `metadata` / `private` / `public`. Comprueba hosts de metadata (`metadata.google.internal`, `metadata.goog`, `metadata.azure.internal`, `169.254.169.254`), IPs literales y **resuelve el hostname por DNS comprobando todas las direcciones** (mitigación básica de DNS rebinding). Cubre IPv4 (loopback, RFC1918, link-local, CGNAT, benchmarking, this-network) e IPv6 (`::1`, `fc00::/7` ULA, `fe80::/10`, IPv4-mapped).
- `isLocalRequest(headers)`: sin `X-Forwarded-For` la conexión es directa → local (caso soportado: uso en la propia máquina). Tras el proxy (Caddy), la primera entrada de XFF decide: IP privada → red local; IP pública → remoto.

### `src/app/api/models/route.ts`
1. Petición remota + `http:` → `400` (el proveedor debe usar https).
2. Destino `metadata` → `403` siempre.
3. Destino `private` + petición remota → `403`. Destino `private` + petición local → permitido (preserva el caso legítimo de Ollama en `localhost:11434`, documentado en los presets del Model Studio).

## Verificación
- **20/20 tests unitarios PASS** de `isPrivateIp` e `isLocalRequest` (IPv4/IPv6, XFF múltiple, `unknown`, loopback, CGNAT, mapeadas).
- **Smoke tests en caliente** contra el build de producción real:
  - `https://metadata.google.internal` → `403 Destino bloqueado: endpoint de metadata de nube`.
  - `http://192.168.1.10` con XFF remoto → bloqueado.
  - `http://127.0.0.1:11434` sin XFF (Ollama local) → guard permite; falla solo la conexión (comportamiento esperado sin Ollama).
  - `http://api.deepseek.com` con XFF remoto → `400` exige https.
  - `https://api.deepseek.com` con key inválida → atraviesa el guard y devuelve el `401` real del proveedor (flujo legítimo intacto).

## Limitaciones y siguientes pasos
- La clasificación local se basa en `X-Forwarded-For`: un cliente que alcanza el puerto de la app **directamente desde Internet** (sin proxy delante) aparece como local. El guard es defensa en profundidad; la barrera real contra exposición es de despliegue (no publicar el puerto / auth en el proxy). El README lo advierte ahora explícitamente.
- R4 (APIs sin autenticación): **no se implementó auth** en esta ronda por decisión conservadora — cualquier token rompería la UX actual del cliente. Queda registrado como pendiente con dos opciones: middleware con token opcional vía `.env` (requiere soporte en la UI) o autenticación en el proxy inverso. Priorizar si hay previsión de despliegue no local.
- Rate limit en `POST /api/campaigns` (recomendación 4): pendiente, ligado a la decisión de autenticación.
- Historia de git con `.env`/BD antiguos (R7): sin acción — verificado en Ronda 1 que no contienen claves reales; reescribir historia es más riesgoso que el residual actual.
