## 3. El estándar, formulado para su adopción
Para todo punto de red nuevo que llegue con features, el estándar del proyecto (patrón ya canónico en el guard) es:

1. **Plazo explícito obligatorio**: `AbortSignal.timeout` si la API es abortable (`fetch`); `withTimeout`/`Promise.race` si no lo es (creación de SDK); wrapper `setTimeout`+`clearTimeout` si la librería no trae plazo propio (DNS de `node:dns`).
2. **Dependencia inyectable**: la operación de red se recibe como parámetro opcional con default real (`lookupFn: LookupFn = dnsLookup`), para tests herméticos sin red ni DNS.
3. **Degradación explícita al contrato existente**: el vencimiento del plazo produce el mismo resultado que el error de red ya manejado (p. ej. `'public'` en el guard, `null` en el LLM) — nunca un colgado ni una excepción no contemplada.
4. **Sin temporizadores huérfanos**: `clearTimeout` en todos los desenlaces.
5. **Tres tests mínimos**: resuelto, rechazado y **colgado** (el contrato del plazo es el que se prueba).

Quiero dejar constancia de que este estándar es descriptivo, no nuevo: es exactamente lo que ya aplican los 6 puntos vigentes. Su formalización como convención citable (análoga a la convención `Suspense` ratificada en D6) es decisión del Director; sugerencia de ubicación si se adopta: una línea en el §8 del PROTOCOLO o en el README, a cargo del propietario que el Director designe.
